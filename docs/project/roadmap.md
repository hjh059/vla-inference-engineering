# 条件性项目路线图

> 当前只有 Phase 0：Problem Discovery 获得授权。后续阶段是否存在、解决什么问题和采用什么架构，均取决于 Phase 0 证据。

## 当前状态

| 阶段 | 状态 | 退出结果 |
|---|---|---|
| Phase 0：Problem Discovery | 进行中 | Continue / Contribute upstream / Stop or Pivot |
| Phase 1：问题立项与最小解法 | 条件性、未授权 | 仅解决已验证问题的最小方案 |
| Phase 2：场景验证 | 条件性、未授权 | 证明方案解决原问题且未引入不可接受退化 |
| Phase 3：目标环境验证 | 条件性、未授权 | 在问题声明要求的真实环境形成证据 |
| Phase 4：交付加固 | 条件性、未授权 | 仅在真实交付需求存在时实施 |

## Phase 0：Problem Discovery

- 从真实 Issue 固定候选用户、受影响版本和一条具体工作流；
- 使用问题原生路径完成最小复现并建立预期行为或正确性基线；
- 定位根因，在适当层级和语言中完成最小修复与回归；
- 使用与问题影响匹配的数值比较、LIBERO、最小仿真或控制端测试；
- 仅在相关时使用 `vla.cpp`、`Embodied.cpp`、GR00T 官方部署或其他实现作为对照、诊断和上游贡献工具；
- 记录首个稳定问题；
- 使用上游版本和替代方案反证；
- 决定继续独立项目、向上游贡献或停止/转向。

详细步骤见 [Problem Discovery 计划](../plans/phase-0.md)。

## Phase 1：问题立项与最小解法

只有 Phase 0 得出 `Continue` 才定义本阶段。届时重新确认：

- 具体用户、工作流、问题和影响；
- 已排除的现有方案；
- 最小解决边界和明确非目标；
- 由问题影响推导的验收指标；
- 是否需要新的实现、测试和架构 ADR。

本阶段不默认采用现有候选 C++ Runtime、安全进程、ROS2 或 RobotAdapter 设计。

## Phase 2：场景验证

如果最小解法需要闭环或系统级验证，再固定与问题匹配的任务、仿真、输入、动作和故障实验。仿真结果不能外推为真机或生产结论。

## Phase 3：目标环境验证

只有问题陈述要求目标 GPU、边缘设备或真实机器人时才进入。性能、功耗、温度、安全和长稳门禁必须由问题影响推导，而不是复用当前候选数字。

## Phase 4：交付加固

只有存在明确交付、分发、升级或设备运营需求时，才评估 SBOM、签名、原子升级、回滚和供应链能力。

## 阶段推进规则

1. 当前阶段必须有固定版本、可重复命令和原始证据；
2. 官方声明、代码检查、本地复现和本地测量分开记录；
3. 未完成替代方案反证前，不创建最终项目架构；
4. 不以增加实现范围代替问题价值证明；
5. `Contribute upstream` 和 `Stop/Pivot` 是成功完成 Problem Discovery 的合法结果；
6. 问题、能力声明和证据等级必须一致。
