# Problem Discovery 范围

> 状态：Problem Discovery。当前范围约束调查活动，不定义最终产品或生产架构。

## 调查目标

识别并验证 VLA 推理与机器人部署中一个真实存在、可重复、尚未被现有方案充分解决且值得投入的问题。

调查必须回答：

1. 谁遇到了问题；
2. 他正在完成什么工作；
3. 当前使用什么方案；
4. 实际发生什么失败或困难；
5. 问题造成什么影响；
6. 现有方案为什么不能解决；
7. 问题是否值得形成独立项目；
8. 应以什么证据判定问题解决。

## 候选调查边界

真实项目 Issue 是问题线索来源，不是预先确定的项目场景或已验证事实。第一问题池采用 LeRobot Issues，优先调查 SmolVLA/LIBERO、异步推理、动作语义、Processor、GPU 内存和控制端消费；Isaac-GR00T Issues 作为第二问题池，重点关注 ONNX/TensorRT、Jetson、跨硬件正确性和性能，不作为默认首个复现路径。

首轮优先调查开源 VLA 从 Issue 报告、问题原生实现到影响验证的路径，包括：

- Issue 中报告的用户、工作流、预期行为、实际行为和影响；
- 受影响版本和问题原生路径的最小复现；
- 预期行为、官方参考或已有测试基线；
- checkpoint、Processor、Runtime、协议或控制端中的根因；
- 与根因匹配的最小修复和回归测试；
- 图像、语言和机器人状态预处理；
- 动作解码、反归一化和语义映射；
- 仿真或机器人接口接入；
- 延迟、超时、Runtime 退出和恢复行为；
- 正确性、性能、测试、制品和许可证证据。

预期行为、官方参考或已有测试可以作为正确性基线。`Embodied.cpp` 可在相关问题下作为 C++ 代码级定位和上游贡献入口，`vla.cpp` 可作为跨实现正确性、性能或能力对照；二者都不是必经路径。GR00T 官方部署路径进入第二问题池的调查范围。以上工具只根据被选问题和固定版本的实际能力启用，不构成生产候选清单或预设解决方案。

受限固定工位中的语言条件拣选与放置仅作为候选问题调查或影响验证负载。它不是已确认产品场景，不代表已有客户、产线、真机案例或 VLA 业务必要性。

## 本阶段必须产出

所有退出结果都必须提交：

- 不超过 10 个候选 Issue 的来源和筛选依据；
- 进入 shortlist 的 Issue、受影响版本、环境和工作流；
- 问题原生路径的复现命令与结果，或无法形成可执行复现的证据；
- 官方声明、代码检查、受控环境复现和测量的证据等级；
- 首个稳定问题的证据，或“未发现有价值缺口”的结论；
- `Continue`、`Contribute upstream` 或 `Stop/Pivot` 决策。

只有稳定问题成立且对应字段适用时才提交：

- 模型、checkpoint、Processor、Runtime、协议、控制端和硬件等相关资产版本；
- 仅覆盖根因假设和替代方案反证所需维度的对照；
- 根因及其代码、配置、数据、资源或协议证据；
- 与根因匹配的最小修复，或无法安全修复的明确结论；
- 能在修复前失败、修复后通过的回归验证；
- 与问题声明匹配的数值、资源、动作、仿真、控制端或异常影响验证。

这些是调查产物，不是生产系统交付物。

## 当前不实施

- 冻结最终项目目标、生产模型、Runtime、后端、硬件或控制路径；
- 新建完整 C++ 推理 Runtime；
- 实现 SafetySupervisor、RobotAdapter 或正式 ROS2 控制链路；
- 扩展生产级测试、制品、签名、发布和回滚系统；
- 多模型在线切换、通用插件框架或云端多租户 Serving；
- VLA 预训练、训练算法、视觉算法或世界模型研究；
- 真实机器人高风险动作或功能安全能力声明。

发现问题所需的最小测试夹具、一次性脚本或隔离环境可以在后续获得授权后实施，但不得演变为未经立项的生产架构。

## 候选验证维度

原文档中的 Observation/Action 契约、动作新鲜度、故障隔离、安全监督、ROS2、性能优化和原子制品设计保留为候选验证维度。只有当复现证据表明它们对应真实问题时，才能进入项目范围和架构决策。

## 资源与硬件约束

- Problem Discovery 默认使用当前本地设备开发和执行能够完成的最小复现；
- 后续操作系统以原生 Ubuntu 桌面版为候选，但具体版本须结合 GPU 驱动、CUDA 和被选 Issue 路径及相关实现的兼容性验证后确定；
- 允许把 Jetson、x86_64 整机升级或临时云 GPU 作为候选资源，但当前不冻结平台或采购方案；
- 只有在最小复现出现稳定、可归因的算力、显存、指令集、驱动或平台兼容性阻塞后，才进入硬件决策；
- 采购或升级前必须比较缩小模型/量化、调整复现路径、临时云 GPU 和现有硬件升级等替代方案；
- 设备价格、岗位展示价值或“更像生产环境”不能单独作为采购依据。

当前设备事实、平台候选和资源升级门禁由[部署平台候选调研](../research/deployment-platforms.md)维护，避免在范围文档中重复易变化的规格。

## 问题成立后的条件性边界

如果 Problem Discovery 证明问题值得独立立项，下一阶段必须重新定义：

- 具体用户和工作流；
- 问题与影响；
- 已排除的替代方案；
- 最小解决边界；
- 任务、输入、输出和失败语义；
- 基于问题影响推导的验收指标；
- 必需实现和明确非目标。

不能直接恢复旧的完整闭环范围；旧候选架构只能作为方案输入重新评估。

## 数据与证据边界

- 官方 README、论文和公开 benchmark 是 `Official claim`，不是本地复现；
- GitHub Issue 只证明有人报告了问题；未核查版本、环境、复现、维护者结论和相关 PR 时，不能将报告内容或归因写成项目事实；
- 代码中没有找到某项能力，只能记录检查范围，不能证明整个项目“不支持”；
- 仿真、公开数据和真机证据分别记录来源、许可证和适用范围；
- 配置错误、环境不兼容、文档缺陷、实现 bug 和设计限制必须区分；
- 一条方案失败后必须检查上游版本和至少一个合理替代方案；
- 没有证据时结论必须为 `Unknown` 或 `Insufficient evidence`。
