# VLA 推理部署与优化基础概念

本文定义并说明完成本项目需要理解的基础概念，覆盖模型训练与推理、VLA 动作生成、推理部署、可复现实验、性能测量、profiling 和优化验证，并作为理解后续项目范围、执行计划和实验记录的概念基础。

本文是概念说明，不记录项目阶段状态、实验配置或性能结论。具体范围、配置和证据分别以[项目范围](../project/scope.md)、[执行计划](../plans/phase-0.md)和[实验记录](../../experiments/README.md)为准。

概念的收录边界是：理解当前项目范围、执行步骤、配置字段和实验结论所必需的通用知识。具体工具的完整使用方法、候选方案细节和随阶段变化的项目事实不在本文重复维护。

## 1. 大模型的核心逻辑

从较高的抽象层面看，当前主流的数据驱动模型基本遵循同一套逻辑：

```text
训练数据
+ 模型结构
+ 训练目标
+ 优化算法
        ↓
不断调整模型参数
        ↓
让模型输出尽量符合训练目标
```

常见数学表达是：找到一组参数 `θ`，使训练数据上的损失函数 `L` 尽可能小。

其中：

- 训练数据决定模型能够看到哪些案例；
- 模型结构决定信息以什么方式被处理；
- 训练目标决定什么样的输出会得到更高评价；
- 优化算法决定如何调整参数以降低损失。

可以把训练数据理解为“教材”，把训练目标理解为“评分规则”。模型学习的是如何在教材和评分规则下取得更高分，而不是直接获得现实世界中的绝对真理。

不同类型的模型具有不同的输入和学习目标：

| 模型 | 输入 | 主要学习目标 |
|---|---|---|
| LLM | 上下文 token | 预测下一个 token 的概率分布 |
| VLA | 图像、语言指令、机器人状态 | 预测专家动作或动作分布 |
| 图像分类模型 | 图像 | 预测人工标注的类别 |
| 扩散图像模型 | 文本、带噪图像 | 学习从噪声生成或恢复图像 |
| 世界模型 | 当前状态和动作 | 预测未来状态 |
| 强化学习策略 | 环境状态 | 最大化长期累计奖励 |

例如，LLM 通常学习：

```text
p(下一个 token | 前面的 token)
```

它不是直接学习“什么是真理”，而是学习在给定上下文中哪些 token 更可能出现。因此，LLM 可能生成语言上合理、事实上却错误的内容。

VLA 则学习：

```text
p(动作 | 图像、指令、机器人状态)
```

它也不是直接理解“唯一正确的动作”，而是从专家示范或奖励信号中学习：在当前条件下，哪些动作更可能合理或成功。

因此，更准确的说法是：

> 大模型通过数据和训练目标学习一个统计映射，使输出接近训练数据、奖励或约束所定义的理想结果。

模型能否接近现实中的正确结果，取决于：

- 数据是否准确、丰富并覆盖实际场景；
- 输入、标签和任务是否正确对应；
- 训练目标是否真正代表任务成功；
- 模型容量和结构是否合适；
- 优化过程是否充分、稳定；
- 推理环境是否接近训练数据分布；
- 是否具有闭环反馈、外部工具和安全约束。

现代模型也可能结合自监督学习、模仿学习、强化学习、人类偏好反馈、合成数据、外部工具以及规则或物理约束。这些方法形式不同，但底层仍然是在利用数据或环境反馈调整模型参数。

## 2. 模型训练的基本过程

模型训练的核心循环是：

1. 向模型提供输入；
2. 模型根据当前参数产生预测；
3. 将预测与训练目标比较，计算损失；
4. 根据损失计算参数的调整方向；
5. 更新参数；
6. 在大量数据上重复上述过程。

可以概括为：

```text
预测 → 计算误差 → 修正参数 → 再次预测
```

更完整的训练过程是：

```text
输入数据
   ↓
前向传播
   ↓
模型预测
   ↓
计算损失
   ↓
反向传播
   ↓
计算参数梯度
   ↓
优化器更新参数
```

### 2.1 参数的作用

神经网络中的基本计算形式类似：

```text
输出 = 输入 × 权重 + 偏置
```

数十亿参数就是训练后得到的大量数值系数。它们共同决定输入信息如何被转换、关联和组合。

知识通常不是存储在某一个参数中，而是分布在大量参数之间：

- 一个概念可能由许多参数共同表示；
- 一个参数也可能参与多种概念和计算；
- 参数保存模型长期学到的转换规律；
- activation 保存本次输入产生的临时中间状态。

### 2.2 损失、反向传播和推理

损失函数评价当前输出与训练目标之间的差距。例如，连续值回归可以使用均方误差：

```text
L = (预测值 - 目标值)²
```

LLM 通常使用交叉熵，使正确下一个 token 的概率更高。VLA 则可能使用动作回归损失、token 交叉熵、扩散去噪目标或 flow-matching 目标。

反向传播回答的是：

> 模型中的每个参数应该向哪个方向调整一点，才能让损失变小？

优化器根据梯度更新参数。训练完成后，普通推理过程通常不再修改参数：

```text
训练阶段：不断调整参数
推理阶段：使用固定参数处理新输入
```

训练的基本循环很直接，但真正困难的是数据质量、输入输出表示、损失设计、大规模稳定优化、泛化以及可靠性验证。可以类比飞机：机翼产生升力的基本原理并不复杂，但制造可靠、安全、可控的飞机仍然是庞大的工程。

## 3. 模型推理与部署路径

训练得到参数后，还需要一条可执行的推理路径把外部输入转换为模型输出：

```text
输入资产
   ↓
预处理与序列化
   ↓
Runtime 加载模型并执行计算
   ↓
后处理与反序列化
   ↓
动作张量或动作序列
```

这条路径中的任何一层发生变化，都可能改变正确性、性能或资源消耗。模型本身与运行模型的软件不是同一概念：

| 概念 | 含义 |
|---|---|
| 模型结构 | 网络由哪些层、算子和数据流组成 |
| Checkpoint | 训练过程中保存的参数及相关状态；推理通常只需要其中与前向计算有关的部分 |
| 模型制品 | 实际交给 Runtime 加载的文件，可能由 checkpoint 转换、合并或量化得到 |
| Runtime | 负责加载模型、组织算子并调度 CPU、GPU 等设备执行推理的软件 |
| Backend | Runtime 面向某类硬件或计算库的具体执行实现，例如 CPU 或 CUDA backend |
| Revision | 代码、模型或配置在版本历史中的确定版本 |
| SHA-256 | 用于核对文件字节身份的摘要；相同摘要说明文件字节相同，不说明其语义或性能正确 |

### 3.1 模型格式、GGUF 与量化

模型格式规定参数、张量元数据和其他信息如何存储。GGUF 是一种模型文件格式或容器，不等同于量化算法，也不天然表示某一种数值精度。同一格式可以保存不同类型和精度的张量。

量化是用更少的位数或更紧凑的数值表示保存和计算模型参数或 activation。它通常可以减少模型大小、内存流量和显存占用，并可能提高推理速度，但也可能引入数值误差；实际收益取决于硬件、backend、算子实现和工作负载，不能只根据文件大小推断。

模型转换还可能改变张量布局、合并辅助模块或补充运行时元数据。只记录模型名称无法确定实际运行的字节和转换过程，因此可复现实验还需要确定上游 checkpoint、转换后制品、转换方法和文件身份；本项目的正式记录要求以[正式基线配置](../project/scope.md#正式基线配置)为准。

### 3.2 预处理、后处理与输出契约

VLA 推理的输入不只是“图像和文字”这一抽象描述。实际路径还会确定：

- 图像尺寸、颜色通道、归一化方式和排列顺序；
- 文本如何 tokenization，以及特殊 token 和序列长度；
- 机器人状态的维度、顺序、单位、归一化和缺失值处理；
- action tensor 的形状、有效维度、填充值及反归一化规则。

这些共同组成输入输出契约。形状正确但预处理、维度语义或反归一化不匹配时，模型仍可能产生数值有限但语义错误的动作。

### 3.3 模型加载、冷启动与稳态请求

模型加载包括读取制品、分配内存、初始化 backend，并可能创建或编译执行所需的资源。首次推理还可能触发额外初始化。因此需要区分：

```text
进程启动 + 模型加载 + 首次初始化 + 单次推理
```

和：

```text
模型已加载 + 同一进程内的重复推理
```

前者反映冷启动或一次性任务体验，后者更接近常驻服务的稳态请求。两者都是合理指标，但回答的问题不同，不能把重复启动 CLI 的总时间当作同进程稳态推理延迟。

### 3.4 CPU、GPU 与 CUDA 软件栈

在典型 CUDA 推理路径中，CPU 负责程序控制、输入处理和提交 GPU 工作，GPU 通过大量并行线程执行 kernel。数据可能需要在主机内存与设备显存之间传输；提交、传输、执行和同步共同构成端到端路径。

CUDA 相关版本需要区分：

| 概念 | 作用 |
|---|---|
| NVIDIA driver | 操作系统与 GPU 通信并支持一定范围的 CUDA 能力 |
| CUDA Toolkit | 编译器、开发库和分析工具等开发组件的集合 |
| CUDA Runtime/API | 应用创建内存、提交 kernel 和进行同步所使用的运行接口 |
| Compute Capability | GPU 架构支持的指令和硬件功能等级，影响二进制编译目标与算子可用性 |

驱动显示的“最高支持 CUDA 版本”、本机安装的 Toolkit 版本和应用实际链接或使用的运行库版本不是同一个值，不能互相替代记录。

CUDA Graphs 等机制可以把一组重复提交的 GPU 工作记录后整体重放，从而减少 CPU 提交开销；它是否改善端到端指标取决于工作负载和实现，仍需通过 profile 与前后测量判断。

## 4. VLA 如何学习机器人动作

VLA 是 Vision-Language-Action，即视觉—语言—动作模型。其典型输入和输出是：

```text
摄像头图像
+ 语言指令
+ 机器人当前状态
        ↓
       VLA
        ↓
未来一段机器人动作
```

许多 VLA 的核心策略训练属于模仿学习或行为克隆。训练数据通常包含：

```text
图像
+ 语言指令
+ 机器人状态
+ 专家实际执行的动作
```

专家动作可以来自人工遥操作、传统控制器、仿真成功轨迹或已有策略生成并筛选出的轨迹。模型从大量轨迹中学习状态、任务和动作之间的统计规律。

VLA 可以简化为两个部分：

```text
图像 + 指令 + 机器人状态
              ↓
       视觉语言主干
              ↓
         条件特征
              ↓
           动作头
              ↓
         动作序列
```

视觉语言主干负责理解场景和任务，动作头负责将条件特征转换为机器人动作。

VLA 还可能包含视觉语言预训练、机器人轨迹微调、多机器人或多任务联合训练、强化学习、偏好优化、蒸馏和量化感知训练。这些属于更完整的训练流程；下面的直接回归、动作 token、扩散和 flow matching 主要描述动作如何建模和生成。

VLA 输出还必须与目标机器人的 embodiment 对齐。Embodiment 表示机器人的具体机体和接口，包括关节数量、坐标系、传感器、夹爪、控制频率以及动作定义。相同数值在不同 embodiment 或动作表示下可能具有完全不同的含义。

动作通常还会在训练前归一化，以便不同维度具有适合学习的数值尺度；推理输出需要使用与 checkpoint 和数据集匹配的统计量反归一化。归一化、维度顺序或单位不一致，都可能使结构合法的输出变成错误控制量。

## 5. VLA 动作头的主要建模方式

| 类型 | 训练方式 | 推理方式 | 主要特点 |
|---|---|---|---|
| 直接回归 | 让预测动作接近专家动作 | 一次输出连续动作 | 简单、快速，但可能对多种合理动作求平均 |
| 自回归动作 token | 预测专家动作对应的离散 token | 像 LLM 一样逐 token 生成 | 可以复用语言模型结构，但需要动作离散化 |
| 扩散 | 学习从带噪动作恢复专家动作 | 从 noise 开始多步去噪 | 能表达多种可能动作，但推理需要多步计算 |
| Flow matching | 学习从 noise 到专家动作的速度场 | 沿速度场进行多步积分 | 支持生成连续的多模态动作分布 |
| CVAE | 学习动作与随机隐变量之间的关系 | 从隐变量采样后生成动作 | 可以表达多种动作模式 |
| 混合密度模型 | 学习多个概率分布及其权重 | 从概率分布中采样动作 | 可以描述多峰动作分布 |

这些方法通常位于更大的模仿学习或行为克隆框架中，不是 VLA 的完整训练方法。

Action chunking 与上述方法属于不同维度。它表示模型一次预测未来多步动作：

```text
一次输入 → 未来 N 步动作
```

直接回归、扩散、flow matching 和 CVAE 都可以用于生成 action chunk。

需要区分 action chunk 长度和实际执行步数。Chunk 长度是一次推理生成的未来动作数量；控制端可以只执行其中前 `K` 步，然后重新观察并规划。执行步数越少，闭环反馈越频繁，但系统留给下一次推理的延迟预算通常越紧；执行步数越多，可以摊薄推理开销，但后半段动作依据的是更早的观察，可能增加开环误差。重规划频率由实际执行步数、机器人控制频率和推理调度共同决定，不能只根据模型输出的 chunk 长度推断。

## 6. 扩散与 Flow Matching

### 6.1 扩散动作头

扩散模型在训练时逐渐给真实动作加入噪声，并学习如何反向去除噪声：

```text
训练：真实动作 → 加噪 → 更强噪声 → 接近纯 noise
                    ↑
               学习反向去噪

推理：随机 noise → 多步去噪 → 合理动作
```

### 6.2 Flow-matching 动作头

Flow matching 学习一个连续的速度场：

```text
dx/dt = vθ(x, t, condition)
```

其中：

- `x` 是当前动作候选；
- `t` 表示生成过程所处的时间；
- `condition` 是图像、指令和机器人状态；
- `vθ` 是模型预测的移动方向。

推理过程可以理解为：

```text
随机 noise
    ↓ 根据速度场移动
中间动作状态
    ↓ 继续积分
最终动作
```

扩散和 flow matching 都是在学习从简单随机分布到复杂动作分布的变换，但两者的训练目标和生成方程不同。Flow matching 经常被通俗地描述为“去噪”，严格来说它学习的是概率分布之间的连续流动。

## 7. Initial Noise 与随机动作生成

采用 flow-matching 动作头的 VLA，其动作生成过程可以简化为：

```text
图像、指令、状态 → 条件特征

initial noise
      ↓
flow-matching 多步变换
      ↓
   动作序列
```

这里的 noise 不是图像噪声或硬件噪声，而是动作生成头的初始随机输入。它的作用包括：

1. 为生成过程提供起点；
2. 表达同一任务下的多种合理动作；
3. 与相应的生成式训练目标共同支持对条件动作分布的建模和采样，而不只是输出多个合理动作的平均值。

不同 noise 可能产生不同动作：

```text
相同图像、指令、状态 + noise A → 动作方案 A
相同图像、指令、状态 + noise B → 动作方案 B
```

相关概念需要区分：

| 概念 | 作用 |
|---|---|
| Initial noise | 模型真正接收的随机输入 |
| Seed | 初始化伪随机数生成器；只有算法、状态、采样顺序等条件一致时，才足以复现相同 noise |
| Temperature | 调整概率分布的平坦程度，不是 noise |
| Token sampling | 从 token 概率分布中抽样 |
| Fixed noise | 直接固定生成起点，用于可复现实验 |

对正确性和性能实验来说，直接固定 noise 可以让基线和优化版本接收字节相同的随机输入，排除随机采样这一项混杂因素。它不能单独保证输出差异只来自实现变化；模型制品、软件版本、硬件环境、其他输入和执行条件也需要受控，并要考虑并行计算可能带来的数值非确定性。固定 noise 是实验控制手段，不表示实际机器人部署时必须永远使用同一份 noise。

不是所有 VLA 都使用 initial noise。只有采用扩散、flow matching 或其他随机生成式动作头的模型通常需要此类随机输入；直接回归或确定性 token 解码可以没有这一过程。

## 8. 如何理解 VLA 输出的“正确”

需要区分接口与结构合法、数值可重复或优化前后回归一致、动作语义正确和闭环任务成功。这些层级回答不同问题，前一层成立不代表后一层成立。

### 8.1 接口与结构合法

原始输出首先应满足已冻结的接口契约，例如：

- 没有 `NaN` 或 `Inf`；
- 维度和形状正确；
- action tensor 的有效维度、填充值和数据类型符合约定；
- 归一化和反归一化与 checkpoint、数据集和机器人匹配。

完成反归一化并映射到具体机器人控制接口后，才可以根据该接口进一步检查关节位置、速度、加速度、单步位移和夹爪取值是否越界。原始模型输出不一定与这些物理量一一对应。

### 8.2 数值可重复与优化前后回归一致性

数值可重复表示在声明的相同条件下重复运行，输出差异处于预先确定的范围内。优化前后回归一致性表示基线实现与优化实现在已冻结的输入和判定标准下都通过正确性检查；它只支持已测范围内的一致性结论，不证明两个实现对所有可能输入普遍等价。两者都不必然要求逐 bit 相同：浮点运算顺序、并行归约、数学库和硬件实现可能造成微小差异。

连续动作的比较对象和判定方式可以包括有效动作维度、绝对误差、相对误差或任务相关容差。事后根据待评估结果选择容差会引入确认偏差，因此判定依据应独立来自输出尺度、参考实现或基线重复性；本项目的冻结时机和正式规则以[执行计划的测量与判定原则](../plans/phase-0.md#测量与判定原则)为准。

### 8.3 动作语义正确

动作语义正确表示每个有效维度的含义、顺序、坐标系、方向、单位、尺度和控制模式与目标机器人接口一致。例如，同一个数值可能表示关节绝对位置、关节增量、末端速度或归一化控制量；如果解释方式错误，即使形状和数值范围合法，也不能作为正确动作执行。

动作语义可以通过 checkpoint 与数据集元数据、预处理和反归一化实现、机器人接口定义以及已知输入输出样本进行核对。它证明的是动作被正确解释，不证明动作序列能够在环境中完成任务。

### 8.4 闭环任务正确

闭环任务正确表示策略在持续观察、执行和重规划过程中能够达到任务目标。它依赖：

- 高质量且覆盖充分的专家轨迹；
- checkpoint 与机器人 embodiment 匹配；
- 正确的图像、状态和动作预处理；
- 合适的动作生成目标；
- 闭环执行和持续重新观察；
- 仿真或真实机器人的任务成功率验证。

典型闭环过程是：

```text
观察
 ↓
预测一段动作
 ↓
执行其中前几步
 ↓
重新观察并再次预测
```

这种滚动预测可以持续修正误差。完整验证通常应逐层进行：

```text
输出结构正确
→ 数值有限且范围合法
→ 固定输入和 noise 下结果可重复
→ 优化前后在已测范围内通过正确性回归
→ 动作尺度和语义正确
→ 闭环任务具有足够成功率
```

## 9. 可复现实验与基线

性能优化不是比较两个孤立的数字，而是在受控条件下只改变目标实现，观察正确性和性能如何变化：

```text
相同模型制品、输入、环境和测量方法
                +
          基线实现 / 优化实现
                ↓
       比较正确性、性能与资源结果
```

基线是优化前的参照实现及其在冻结条件下得到的正确性和性能结果。Configuration 记录一次正式比较的冻结条件以及基线、优化实现 revision 等对比变量。不同冻结条件下得到的结果不能直接组成一组具有因果归因意义的优化前后比较；哪些字段属于冻结条件、何时建立新 `Configuration ID`，完全以[正式基线配置](../project/scope.md#正式基线配置)的规范性定义为准。

需要区分：

| 概念 | 含义 |
|---|---|
| 控制变量 | 在基线和优化比较中保持不变的条件 |
| 对比变量 | 为验证优化而有意改变的实现 |
| 重复性 | 在声明为相同的测量对象、程序、环境和短期运行条件下，重复执行能否得到相符结果 |
| 可复现性 | 根据保存的代码、资产、环境定义和方法独立重建实验时，能否得到相符结果；发生变化的条件也需要明确 |
| 原始样本 | 每次测量直接产生、尚未汇总的数据 |
| 派生结果 | 由原始样本按已记录方法计算出的统计量或结论 |

严格的可复现性不意味着所有浮点值或耗时都逐 bit 相同，而是要求变化处于预先定义且与任务相符的判定范围内。Revision 和 SHA-256 用于确定代码与文件身份，复现命令和环境记录用于确定执行方法；它们相互补充，不能彼此替代。

这里的重复性和可复现性都要求明确“哪些条件相同、哪些条件允许变化”，而不是只根据是否由同一团队执行来区分。

## 10. 性能测量

### 10.1 指标与计时边界

延迟是一次操作从起点到终点经历的时间，吞吐是单位时间内完成的工作量。降低单请求延迟不一定提高最大吞吐，提高并发吞吐也可能增加单个请求的排队时间，因此指标必须与任务场景对应。

主指标直接用于判断优化是否达到当前任务目标；次指标用于描述机制、资源消耗或重要取舍；约束指标给出结果必须满足的边界，例如正确性、显存上限或稳定性。次指标改善不能替代主指标结论，主指标改善也不能越过约束指标。具体指标及其角色属于实验配置，而不是由概念文档预先指定。

同一次 VLA 请求可以有不同的计时边界：

```text
客户端序列化与发送
        ↓
服务端接收与预处理
        ↓
视觉编码 / prefill / 动作生成
        ↓
后处理与响应传输
        ↓
客户端接收与解析
```

其中，视觉编码把图像转换为条件特征；prefill 通常处理本次请求的条件 token 或特征并建立后续计算需要的中间状态；采用扩散或 flow matching 动作头时，动作生成还会经过多次 denoise 或积分步骤。具体阶段名称和边界由 Runtime 实现决定，不能只凭名称假定它包含哪些计算。

端到端延迟覆盖用户实际等待的完整边界；阶段延迟只覆盖其中一部分，用于解释时间分布。缺少起点、终点以及是否包含模型加载、通信和数据处理等边界信息时，延迟数字无法被正确解释。存在异步执行或阶段重叠时，各阶段独立测得的时间之和不一定等于端到端延迟。本项目需要记录的内容以[执行计划的测量与判定原则](../plans/phase-0.md#测量与判定原则)为准。

资源指标描述完成工作所消耗或占用的资源，例如峰值显存、CPU/GPU 利用率、功耗和内存流量。它们可以帮助解释结果，但单独的高利用率或低利用率都不能证明某处就是主要瓶颈。

### 10.2 Warm-up、同步与重复测量

Warm-up 是在正式采样前运行若干次不计入结果的请求，用于让一次性初始化、缓存、内存分配、时钟状态等趋于稳定。预热不是固定应为多少次的通用规则，应通过当前工作负载的短试测确定稳定区间，并与正式样本分开。

CUDA kernel 通常由 CPU 异步提交。只测量 kernel 提交前后的 CPU 墙钟时间，可能在 GPU 完成工作前就停止计时，从而低估实际延迟。计时边界需要通过适合的 CUDA event、显式同步，或包含响应完成的端到端协议保证测到目标工作；同步位置本身也可能改变执行行为，因此它是解释测量结果所需的方法信息。

单次测量容易受到系统调度、温度、时钟和后台负载影响。多次原始样本用于观察分布和波动；重复次数、汇总统计和异常样本处理如果在看到结果后改变，会引入选择偏差。均值反映总体平均，median 对少量极端值较稳健，高 percentile 用于描述尾部延迟；选择哪一种取决于要回答的问题。本项目正式采样的保存和汇总规则以[执行计划的测量与判定原则](../plans/phase-0.md#测量与判定原则)为准。

## 11. Profiling、瓶颈与优化验证

Benchmark 回答“在给定条件下有多快或消耗多少资源”，profiling 回答“时间和资源花在哪里”。两者不能互相替代：只有 profile 没有稳定基线，无法判断热点对端到端结果的影响；只有性能数字没有 profile，也无法可靠解释根因。

Profiler 并不是完全透明的观察者。API trace、硬件计数器采集、调用栈记录和 kernel replay 可能增加开销、改变调度或重复执行部分工作，从而扰动原始时序。带 profiler 运行得到的数据主要用于定位和解释热点；除非测量协议明确验证其计时边界和可比性，否则不能把其中的耗时直接当作无分析器条件下的正式性能结果。

### 11.1 系统级与 kernel 级观察

系统级 trace 展示 CPU 线程、CUDA API、kernel、内存传输和同步在时间轴上的关系，适合发现空闲、等待、频繁 launch、CPU-GPU 串行化和阶段重叠。Kernel 级 profile 进一步观察单个 GPU kernel 的执行特征，例如计算吞吐、内存访问和并行资源使用情况。

常见瓶颈类型包括：

| 类型 | 典型含义 |
|---|---|
| CPU 或调度受限 | GPU 等待 CPU 准备输入、提交工作或处理同步 |
| Kernel launch 受限 | 大量短 kernel 的启动与调度开销占比较高 |
| 数据传输受限 | 主机—设备或设备内数据移动处于关键路径 |
| 计算受限 | 关键 kernel 的主要限制来自计算指令吞吐 |
| 内存受限 | 关键 kernel 的主要限制来自内存带宽、延迟或访问方式 |
| 串行阶段受限 | 某个无法重叠的阶段主导端到端延迟 |

这些是需要证据验证的假设，不应只根据一个利用率百分比或耗时最长的函数名称下结论。热点表示消耗时间较多；主要瓶颈则表示改进它有望实质改善目标指标。热点可能不可优化，也可能不在目标指标的关键路径上。

### 11.2 从假设到因果证据

有效的优化闭环是：

```text
稳定基线
   ↓
profile 观察
   ↓
提出可证伪的瓶颈假设
   ↓
只改变与假设对应的实现
   ↓
正确性回归 + 相同条件下重新测量
   ↓
确认收益、代价和适用边界
```

如果某阶段只占端到端时间的一小部分，即使将它完全消除，整体收益也受到该占比限制。因此应优先处理目标指标关键路径上的主要瓶颈，而不是孤立追求某个 kernel 的最大加速比。

性能提升只有在正确性标准仍满足、比较条件一致且原始结果支持时才成立。显存增加、数值误差变化、吞吐与延迟之间的取舍也属于优化结果，不能只报告最快数字。

## 12. 证据层级与本项目的关系

部署 smoke、正式基线、benchmark、profile 和优化后验证回答的问题不同：

| 活动 | 主要回答的问题 |
|---|---|
| Smoke test | 路径能否在声明环境中完成最小运行并产生基本合法输出 |
| 正确性基线 | 冻结输入和判定方法后，参照实现应产生什么结果 |
| 性能基线或 benchmark | 冻结测量方法后，参照实现的性能和资源结果是什么 |
| Profiling | 时间、等待和资源消耗分布在哪里，什么证据支持瓶颈假设 |
| 优化后验证 | 在正确性不回归的前提下，目标实现是否因预期机制而改善 |

各层证据不能相互替代：结构合法只能证明推理链路能够产生符合接口的输出，数值一致性用于比较实现变化，动作语义和任务成功率需要独立的闭环评测；公开 benchmark 和官方声明也不能替代固定配置下的本地测量。
