# 可复现实验、性能测量与优化验证

本文说明如何在受控条件下建立 VLA 推理基线、解释性能测量、使用 profiling 定位瓶颈，并验证优化结果。它不定义本项目当前的配置或阶段结论；规范性字段与实验结果分别以[项目范围](../project/scope.md)和[实验记录](../../experiments/README.md)为准。

## 可复现实验与基线

性能优化不是比较两个孤立数字，而是在受控条件下只改变目标实现，观察正确性、性能和资源结果：

```text
相同模型制品、输入、环境和测量方法
                +
          基线实现 / 优化实现
                ↓
       比较正确性、性能与资源结果
```

基线是优化前的参照实现及其在冻结条件下得到的正确性和性能结果。正式比较中，Configuration 记录冻结条件及基线、优化实现 revision 等对比变量；不同冻结条件的结果不能直接组成具有因果归因意义的前后比较。

| 概念 | 含义 |
|---|---|
| 控制变量 | 基线和优化比较中保持不变的条件 |
| 对比变量 | 为验证优化而有意改变的实现 |
| 重复性 | 在声明相同的对象、程序、环境和短期运行条件下，重复执行能否得到相符结果 |
| 可复现性 | 根据保存的代码、资产、环境定义和方法独立重建实验时，能否得到相符结果 |
| 原始样本 | 每次测量直接产生、尚未汇总的数据 |
| 派生结果 | 由原始样本按已记录方法计算出的统计量或结论 |

严格的可复现性不要求全部浮点值或耗时逐 bit 相同，而要求变化处于预先定义、与任务相符的范围内。Revision 和 SHA-256 确定代码与文件身份，复现命令和环境记录确定执行方法；它们互相补充，不能替代。

## 性能测量

延迟是一次操作从起点到终点经历的时间，吞吐是单位时间完成的工作量。降低单请求延迟不必然提升最大吞吐；提高并发吞吐也可能增加排队时间，因此指标必须与任务场景对应。

主指标用于判断优化是否达到目标，次指标描述机制、资源消耗或取舍，约束指标给出结果必须满足的边界（如正确性、显存上限、稳定性）。次指标改善不能替代主指标结论，主指标改善也不能越过约束。

同一 VLA 请求可有不同计时边界：

```text
客户端序列化与发送
        ↓
服务端接收与预处理
        ↓
视觉编码 / prefill / 动作生成
        ↓
后处理与响应传输
        ↓
客户端接收与解析
```

端到端延迟覆盖用户实际等待的完整边界；阶段延迟只覆盖其中一部分，用于解释时间分布。每个数字都应说明起点、终点，以及是否包含模型加载、通信和数据处理。异步执行或阶段重叠时，独立阶段时间之和不一定等于端到端延迟。

资源指标如峰值显存、CPU/GPU 利用率、功耗和内存流量可帮助解释结果，但单独的高或低利用率不能证明主要瓶颈。

### Warm-up、同步与重复测量

Warm-up 是正式采样前不计入结果的请求，用于使一次性初始化、缓存、内存分配和时钟状态趋于稳定。预热次数不应由通用习惯预设，应通过当前工作负载的短试测确定稳定区间，并与正式样本分开。

CUDA kernel 通常由 CPU 异步提交；只测量提交前后的 CPU 墙钟时间可能在 GPU 完成前停止计时，因而低估实际延迟。计时边界应由适合的 CUDA event、显式同步或包含响应完成的端到端协议保证。同步位置也可能改变执行行为，因此属于必须记录的方法信息。

单次测量会受系统调度、温度、时钟和后台负载影响。多次原始样本用于观察分布和波动；重复次数、汇总统计和异常样本处理不能在看到结果后随意调整。均值反映总体平均，median 对少量极端值较稳健，高 percentile 描述尾部延迟；选择依据应与待回答的问题一致。

## Profiling、瓶颈与优化

Benchmark 回答“给定条件下有多快、消耗多少资源”，profiling 回答“时间和资源花在哪里”。两者不能互相替代：没有稳定基线无法判断热点对端到端的影响；没有 profile 的性能数字也难以可靠解释根因。

Profiler 并非完全透明。API trace、硬件计数器、调用栈记录和 kernel replay 可能增加开销、改变调度或重复部分工作。因此 profile 数据主要用于定位和解释热点；除非测量协议另有验证，不能将其耗时直接作为无分析器条件下的正式性能结果。

### 系统级与 kernel 级观察

系统级 trace 展示 CPU 线程、CUDA API、kernel、内存传输和同步的时间关系，适合发现空闲、等待、频繁 launch、CPU-GPU 串行化和阶段重叠。Kernel 级 profile 进一步观察单个 GPU kernel 的计算吞吐、内存访问和并行资源使用。

| 类型 | 典型含义 |
|---|---|
| CPU 或调度受限 | GPU 等待 CPU 准备输入、提交工作或处理同步 |
| Kernel launch 受限 | 大量短 kernel 的启动与调度开销占比较高 |
| 数据传输受限 | 主机—设备或设备内数据移动处于关键路径 |
| 计算受限 | 关键 kernel 的主要限制来自计算指令吞吐 |
| 内存受限 | 关键 kernel 的主要限制来自内存带宽、延迟或访问方式 |
| 串行阶段受限 | 某个无法重叠的阶段主导端到端延迟 |

这些都是待证实的假设。热点只表示耗时较多；主要瓶颈还要求它位于目标指标的关键路径，且改进它预期会实质改善目标指标。

### 从假设到因果证据

```text
稳定基线
   ↓
profile 观察
   ↓
提出可证伪的瓶颈假设
   ↓
只改变与假设对应的实现
   ↓
正确性回归 + 相同条件下重新测量
   ↓
确认收益、代价和适用边界
```

一个阶段若只占端到端时间的一小部分，即便完全消除，整体收益仍受该占比限制。应优先处理目标指标关键路径上的主要瓶颈，而非孤立追求某个 kernel 的最高加速比。

性能提升只有在正确性标准仍满足、比较条件一致且原始结果支持时才成立。显存增加、数值误差变化、吞吐与延迟之间的取舍也属于优化结果，不能只报告最快数字。

## 证据活动的边界

| 活动 | 主要回答的问题 |
|---|---|
| Smoke test | 路径能否在声明环境完成最小运行并产生基本合法输出 |
| 正确性基线 | 冻结输入和判定方法后，参照实现应产生什么结果 |
| 性能基线或 benchmark | 冻结测量方法后，参照实现的性能和资源结果是什么 |
| Profiling | 时间、等待和资源消耗分布在哪里，什么证据支持瓶颈假设 |
| 优化后验证 | 在正确性不回归的前提下，目标实现是否因预期机制而改善 |

这些证据不能互相替代：结构合法只能说明推理链路输出符合接口，数值一致性用于比较实现变化，动作语义与任务成功率需要独立的闭环评测；公开 benchmark 和官方声明也不能替代固定配置下的本地测量。
