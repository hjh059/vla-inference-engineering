# Phase 0：Problem Discovery 计划

> 状态：进行中。Phase 0 不建设生产系统，不冻结最终项目目标或架构。

## 目标

识别并验证 VLA 推理与机器人部署中一个真实存在、可重复、尚未被现有方案充分解决且值得投入的问题，并通过根因分析、最小修复和影响验证决定后续方向。

Phase 0 不是模型—后端—硬件联合选型，也不以完成一条新的 C++ 安全控制闭环为默认成功结果。没有有价值的独立缺口时，停止、转向或向现有项目贡献同样是合法结论。

## 证据规则

所有能力声明标记为以下等级之一：

| 等级 | 含义 | 可以支持的结论 |
|---|---|---|
| `Official claim` | 官方仓库、文档或论文明确声明 | 进入调查，不代表本地可用 |
| `Code inspected` | 在固定 commit 和文件范围内检查代码 | 说明检查到的实现，不证明整个项目不存在其他路径 |
| `Locally reproduced` | 本项目在固定输入和受控环境下成功重复运行 | 说明该路径在声明环境可运行 |
| `Locally measured` | 本项目在受控环境中保存原始样本、日志和测量方法 | 支持该环境内的定量结论 |
| `Unknown` | 证据不足 | 不得表达为支持或缺失 |

受控环境可以是当前设备、借用设备、Jetson 或设有费用上限的云资源；`Locally` 表示由本项目控制输入、执行和证据，不限定物理位置。

任何失败首先分类为配置错误、环境不兼容、文档缺陷、实现 bug、能力缺失或设计限制。不能把第一次构建失败直接写成现有方案的产品缺口。

GitHub Issue 是候选问题来源，不属于上述能力证据等级。它可以证明有人报告了某个工作流、现象或影响，但不能单独证明归因正确、问题在当前版本仍存在、现有方案不能解决或问题值得独立立项。进入本地复现前必须固定 Issue permalink、相关版本、环境、维护者回应和关联 PR。

## 1. 资源门禁

在选择模型、实现或 Runtime 前记录：

- CPU、内存、GPU、显存、driver、CUDA 和操作系统；
- 可用磁盘、下载条件和模型许可证约束；
- 可持续使用的仿真环境；
- 是否存在可控真机及允许的测试等级；
- 每条路径允许投入的时间上限。

当前默认路径是在现有本地设备上完成开发和最小复现。已确认的宿主机基线为 Intel Core i7-7700HQ、32 GiB 内存、GeForce GTX 1060 6 GiB，以及 128 GB SSD + 1 TB HDD；当前 WSL 会话不能直接访问 GPU，不等同于宿主机没有 GPU。详细事实和兼容性边界见[部署平台候选调研](../research/deployment-platforms.md)。

硬件决策遵循以下顺序：

1. 先在本地完成不依赖更高规格设备的代码检查、构建、输入固定和 CPU/小模型 smoke test；
2. 若被选路径需要本地 GPU，再切换到原生 Ubuntu 验证驱动、CUDA、相关实现和最小模型；
3. 只有出现能够重复、且已排除配置错误的资源阻塞时，才定义所需显存、算力、架构、功耗或 I/O 指标；
4. 使用同一最小复现比较 Jetson、x86_64 整机升级和临时云 GPU，不预设任一方案胜出；
5. 记录成本、复现收益和问题相关性后，再作出购买、升级、租用或保持现状的决定。

可归因的资源阻塞至少需要保存失败命令、固定环境、原始日志和资源测量。仅凭公开模型规模、厂商性能数字或预期的未来需求，不触发采购。

## 2. 收集和筛选候选 Issue

第一问题池采用 LeRobot Issues，优先调查：

- SmolVLA/LIBERO 复现；
- 异步推理与控制端消费；
- 动作维度、归一化、时序和其他动作语义；
- Tokenizer、Processor、机器人状态和图像预处理；
- GPU 内存、延迟和资源释放；
- 推理结果进入仿真或控制端时的可观察失败。

Isaac-GR00T Issues 作为第二问题池，重点关注 ONNX/TensorRT、Jetson、跨硬件正确性和性能。考虑到当前硬件与验证成本，它不作为默认首个复现路径；只有 LeRobot 候选不足、问题需要跨方案反证，或存在当前资源可承担的最小路径时才前移。

首批候选 Issue 总数不得超过 10 个。详细记录统一维护在[候选 Issue 筛选表](../research/issue-candidates.md)，按以下维度筛选：

1. **真实性**：是否包含实际用户、工作流、版本、预期/实际行为、日志或维护者确认；
2. **本地可复现性**：当前设备或可设置费用上限的临时资源能否构造固定输入；
3. **技术深度**：是否需要分析模型、Processor、Runtime、异步调度、GPU 内存、协议、正确性或控制端，而不是单纯安装问答；
4. **硬件成本**：是否必须先购买设备，是否可以用 CPU、小模型、云 GPU 或已有日志验证；
5. **已有解决**：最新版本、workaround、已合并修复或活跃 PR 是否已经解决。

筛选后最多选择两个候选进行复现准备，并只允许一个作为首个主复现路径。已有 PR 不自动排除候选：已合并且可验证的修复用于反证，未合并 PR 可以指向 `Contribute upstream`，但不能包装成新的独立项目。

推荐证据链为：

```text
LeRobot / Isaac-GR00T Issue 提供真实用户问题线索
  → 问题原生实现提供最小复现
  → 预期行为、官方参考或已有测试提供基线
  → 在模型、Processor、Runtime、协议或控制端定位根因
  → 使用与根因匹配的语言和工具完成最小修复与回归
  → 执行与问题声明匹配的影响验证
```

在选出稳定问题前，不实施完整 Runtime，也不购买硬件。

## 3. 固定候选用户和工作流

首个候选用户：需要把开源 VLA 接入本地仿真或机器人控制链路的部署工程师。

首轮从以下工作流中只选择一条：

```text
固定 Issue、版本、环境和输入
  → 问题原生路径最小复现
  → 建立预期行为或正确性基线
  → 定位根因
  → 最小修复与回归测试
  → 与问题声明匹配的影响验证
```

选择前必须说明该工作流的用户、期望结果和失败影响。候选用户尚未验证时明确标为 Hypothesis。

## 4. 建立问题相关基线与对照

根据被选 Issue 调查：

- 受影响上游实现、已有测试和相关 PR；
- 预期行为、官方参考或其他可解释的正确性基线；
- 与根因直接相关的模型、Processor、Runtime、协议或控制端；
- 仅在相关时使用 `vla.cpp` 做跨实现正确性、性能或能力对照；
- 仅在相关时使用 `Embodied.cpp` 做 C++ 代码级复现、定位或上游贡献；
- GR00T 官方 ONNX/TensorRT 部署主要用于第二问题池和跨硬件对照。

仅按固定 commit 比较与被选 Issue、根因假设和替代方案反证直接相关的维度；以下列表不是全量门禁：

- 模型和硬件支持；
- 受影响实现、语言边界和运行时依赖；
- Tokenizer、Processor 和 checkpoint 转换；
- 正确性验证和动作语义；
- 仿真、机器人和 ROS2 接入；
- 请求并发、过期结果、timeout 和退出行为；
- 性能、内存和硬件限制；
- 测试、CI、制品、许可证和项目成熟度。

调研文档保存会变化的生态事实，不提前得出生产选型。

## 5. 选择最小复现路径

路径必须同时满足：

- 被报告问题、受影响版本和原生实现可获得；
- 当前资源能够运行；
- 可以固定输入、预期行为和可观察失败；
- 可以形成根因假设并设计能够证伪的检查；
- 可以增加回归验证；
- 问题声称影响动作或控制时，有最小仿真或消费端验证路径。

优先选择规模最小、变量最少的路径。不能为了保留原架构而选择超出当前资源的模型或硬件。

## 6. 最小调查阶梯

### 6.1 问题原生路径复现

固定 Issue permalink、仓库 commit、输入、命令和环境；适用时再固定 checkpoint、Processor、Tokenizer、seed/noise 或其他模型资产。先在报告所对应的原生实现中观察预期与实际差异，保存标准输出、错误、版本和产物哈希。

### 6.2 基线与根因定位

使用预期行为、官方参考、已有测试或可解释的替代实现建立基线。通过最小化输入、二分版本、检查中间结果或资源行为，把问题定位到模型、Processor、Runtime、协议、控制端或环境；没有证据时保持 `Unknown`。

### 6.3 最小修复与回归

在根因所在层级和上游现有工具链中完成最小修复，不预设 Python、C++、CUDA/TensorRT、Processor、协议或控制端。新增修复前失败、修复后通过的回归验证；无法安全修复时记录原因和最小上游报告。

### 6.4 正确性与影响验证

根据问题声明比较动作、关键中间结果、内存、延迟、协议消息或控制端行为。声称影响实际动作时，固定 simulator、task、初始状态、seed、步数、控制频率和成功判定，执行 LIBERO 或最小仿真；不能把局部数值修复直接表达为闭环问题已解决。

### 6.5 条件性异常观察

只有被选 Issue 涉及延迟、请求超时、资源释放、Runtime 退出或控制消费时，才执行对应的最小异常实验。不为展示系统能力额外实现 SafetySupervisor、队列或恢复系统。

问题候选必须记录：


“缺少某个预设组件”不是问题陈述；必须记录用户工作流中可观察的失败和影响。

## 8. 替代方案反证

对每个稳定问题检查：

1. 上游最新版本或官方推荐配置是否已经解决；
2. 同一项目是否存在另一条文档化路径；
3. 相关时，`vla.cpp`、`Embodied.cpp`、官方部署或其他合理方案是否已经解决；
4. 问题是否只需要文档修正、配置修正或小型上游补丁；
5. 问题是否只在不现实的自设约束中发生。

没有完成反证，不得进入独立项目立项。

## 退出条件

### Continue

形成以下问题陈述，并提交完整证据：

> 对于【具体用户】，在使用【现有方案】完成【具体工作】时，会稳定发生【可重复观察的问题】，导致【可量化或明确的影响】。现有【替代方案】因为【证据支持的原因】不能解决。本项目将只解决【问题边界】，并以【可验证指标】判断成败。

必须同时具备：

- 问题复现命令；
- 固定输入和环境；
- 原始日志或报告；
- 根因及其支持证据；
- 最小修复或无法安全修复的明确结论；
- 修复前后回归及与问题声明匹配的影响验证；
- 现有方案对照；
- 影响说明；
- 基于影响推导的成功与失败指标。

### Contribute upstream

问题真实且可重复，但边界属于现有项目，适合提交 Issue、最小复现或 PR，不成立独立 Runtime 项目。

### Stop/Pivot

未发现有价值缺口、影响不足、资源无法支持，或合理替代方案已经解决。记录证据后停止或重新选择主题，不通过扩大架构掩盖结论。

## 问题成立后的条件性工作

只有 `Continue` 后才重新评估：

- 最终任务、输入/输出 Schema 和用户验收；
- 是否需要自建 C++ 组件；
- 是否需要 ROS2、安全监督、动作生命周期或故障恢复；
- 模型、Runtime、后端、硬件和控制路径；
- 测试、制品、发布和回滚边界；
- 新的 Proposed/Accepted ADR。

旧架构文档和 ADR 只作为候选设计输入，不自动恢复为实施依据。
