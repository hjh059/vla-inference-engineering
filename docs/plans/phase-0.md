# Phase 0：Problem Discovery 计划

> 状态：进行中。Phase 0 不建设生产系统，不冻结最终项目目标或架构。

## 目标

识别并验证 VLA 推理与机器人部署中一个真实存在、可重复、尚未被现有方案充分解决且值得投入的问题，并通过根因分析、最小修复和影响验证决定后续方向。

Phase 0 不是模型—后端—硬件联合选型，也不以完成一条新的 C++ 安全控制闭环为默认成功结果。没有有价值的独立缺口时，停止、转向或向现有项目贡献同样是合法结论。

## 证据规则

所有能力声明标记为以下等级之一：

| 等级 | 含义 | 可以支持的结论 |
|---|---|---|
| `Official claim` | 官方仓库、文档或论文明确声明 | 进入调查，不代表本地可用 |
| `Code inspected` | 在固定 commit 和文件范围内检查代码 | 说明检查到的实现，不证明整个项目不存在其他路径 |
| `Locally reproduced` | 本项目在固定输入和受控环境下成功重复运行 | 说明该路径在声明环境可运行 |
| `Locally measured` | 本项目在受控环境中保存原始样本、日志和测量方法 | 支持该环境内的定量结论 |
| `Unknown` | 证据不足 | 不得表达为支持或缺失 |

受控环境可以是当前设备、借用设备、Jetson 或设有费用上限的云资源；`Locally` 表示由本项目控制输入、执行和证据，不限定物理位置。

任何失败首先分类为配置错误、环境不兼容、文档缺陷、实现 bug、能力缺失或设计限制。不能把第一次构建失败直接写成现有方案的产品缺口。

GitHub Issue 是候选问题来源，不属于上述能力证据等级。它可以证明有人报告了某个工作流、现象或影响，但不能单独证明归因正确、问题在当前版本仍存在、现有方案不能解决或问题值得独立立项。进入本地复现前必须固定 Issue permalink、相关版本、环境、维护者回应和关联 PR。

## 测量与判定原则

- 固定受影响版本或 commit、环境、输入和复现命令；
- 保存原始日志、失败样本和未加工测量结果；
- 指标和验证方式必须由问题声明的影响推导，并在看到修复结果前固定；
- 不得为了让结果通过而降低标准或扩大、缩小问题定义；
- 证据不足只能得出 `Insufficient evidence`，不能判定成功；
- 只记录与问题相关的实验字段，不适用项标记 `N/A` 并说明原因；
- 不能为了填满模板而增加跨实现比较、LIBERO、仿真、控制端或长稳实验。

## 1. 资源门禁

当前默认使用已有设备完成调查。对每个 shortlist 只记录复现实际需要的资源和时间上限；不涉及 GPU、仿真或机器人时填写 `N/A`。

当前设备、受控云资源、Jetson 和整机升级的事实与采购门禁只在[部署平台与资源策略](../research/deployment-platforms.md)维护。资源不足会降低主动复现优先级或使候选进入 `Backlog`，不能据此判定问题不存在。

## 2. 收集和筛选候选 Issue

问题池顺序、评分和动态状态只在[候选 Issue 筛选表](../research/issue-candidates.md)维护。首批总数不超过 10 个，最多两个进入复现准备，同时只执行一个主动复现路径。

Issue 热度、技术趣味、易修复性或适合某种语言不增加真实性；本地资源只影响优先级。最小修复是稳定问题成立后的目标，不是 shortlist 条件。

已有 PR 不自动排除候选：已合并且可验证的修复用于反证，未合并 PR 可以指向 `Contribute upstream`，但不能包装成新的独立项目。

推荐证据链为：

```text
LeRobot / Isaac-GR00T Issue 提供真实用户问题线索
  → 问题原生实现提供最小复现
  → 预期行为、官方参考或已有测试提供基线
  → 在模型、Processor、Runtime、协议或控制端定位根因
  → 使用与根因匹配的语言和工具完成最小修复与回归
  → 执行与问题声明匹配的影响验证
```

在选出稳定问题前，不实施完整 Runtime，也不购买硬件。

## 3. 执行主动复现路径

只有同时固定 Issue、用户或候选用户、工作流、受影响版本、环境、输入、预期行为和可观察影响，候选才进入主动复现。当前资源无法运行时转入 `Backlog`，不判定问题不存在。

执行顺序：

1. 在问题原生路径复现实际行为，保存命令、日志和失败样本；
2. 使用预期行为、官方参考或已有测试建立基线；
3. 通过最小化输入、二分版本和检查相关中间状态定位根因；
4. 稳定问题成立后，在根因所在层级完成最小修复，或记录无法安全修复、缺少专有资产或投入过大的结论；
5. 增加修复前失败、修复后通过的回归，并按问题声明验证实际影响；
6. 检查最新版本、相关 PR 和合理替代方案。

实现语言和工具由问题决定。跨实现比较、LIBERO、仿真、控制端、性能或异常实验只在问题声明需要时执行。

## 4. 记录稳定问题

问题候选必须记录：

```text
Candidate problem ID:
Candidate user:
Workflow and expected outcome:
Repository and commit:
Fixed environment and input:
Reproduction command:
Expected behavior:
Observed behavior:
Repeat count:
Raw log/report:
Direct impact:
Initial classification:
Known workaround:
Existing fixes, PRs or alternatives and why insufficient:
Evidence level:
Root cause and supporting evidence:
Minimal fix or reason not fixed:

```

“缺少某个预设组件”不是问题陈述；必须记录用户工作流中可观察的失败和影响。

## 5. 替代方案反证

对每个稳定问题检查：

1. 上游最新版本或官方推荐配置是否已经解决；
2. 同一项目是否存在另一条文档化路径；
3. 其他合理实现、配置或工作流是否已经解决；
4. 问题是否只需要文档修正、配置修正或小型上游补丁；
5. 问题是否只在不现实的自设约束中发生。

没有完成反证，不得进入独立项目立项。

## 退出条件

### Continue

形成以下问题陈述，并提交完整证据：

> 对于【具体用户】，在使用【现有方案】完成【具体工作】时，会稳定发生【可重复观察的问题】，导致【可量化或明确的影响】。现有【替代方案】因为【证据支持的原因】不能解决。本项目将只解决【问题边界】，并以【可验证指标】判断成败。

必须同时具备：

- 问题复现命令；
- 固定输入和环境；
- 原始日志或报告；
- 根因及其支持证据；
- 最小修复或无法安全修复的明确结论；
- 修复前后回归及与问题声明匹配的影响验证；
- 现有方案对照；
- 影响说明；
- 基于影响推导的成功与失败指标。

### Contribute upstream

问题真实且可重复，但边界属于现有项目，适合提交 Issue、最小复现或 PR，不成立独立 Runtime 项目。

### Stop/Pivot

未发现有价值缺口、影响不足、资源无法支持，或合理替代方案已经解决。记录证据后停止或重新选择主题，不通过扩大架构掩盖结论。

`Continue` 只授权基于已验证问题另行定义下一步，不预先规定架构、阶段或交付物。
